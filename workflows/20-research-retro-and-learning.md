# Workflow 20: Research Retrospective and Learning

## Purpose
Conduct a structured retrospective after each major research project or at regular intervals. Examine what worked well, what did not work, what surprised the team, and what lessons should be carried forward. Update the squad's methodology, playbooks, and training materials based on accumulated learning.

## Trigger
- A major research project (complexity > 0.7) is fully delivered and feedback received.
- Quarterly retrospective cycle (regardless of project size).
- A research project fails audit or receives negative requester feedback.
- Research Lead calls a special retrospective after an unusual project.

## Agents Involved
- **Research Lead**: Facilitates the retrospective and owns the action items.
- **All Participating Agents**: Every agent who worked on the project contributes observations.
- **Quality Auditor**: Provides audit data and quality trend context.
- **Registry Keeper**: Records retrospective outputs and updates institutional memory.

## Inputs
- Complete project record (all workflow artifacts from Workflows 00-16).
- Audit report and quality score from Workflow 13.
- Requester feedback (satisfaction, complaints, praise).
- Time tracking data (planned vs. actual per phase).
- Quality review report from Workflow 19 (if recent).
- Lessons-learned registry (entries from prior retrospectives for pattern tracking).

## Steps

1. **Set the retrospective scope**: Define what is being reviewed:
   - Single project retrospective: focus on one completed research project.
   - Periodic retrospective: review multiple projects over a time window.
   - Incident retrospective: focus on a specific failure or quality issue.
   - Set the time box for the retrospective session (recommended: 60-90 minutes equivalent).

2. **Gather individual observations**: Before the group discussion, each participating agent prepares:
   - **What went well**: Specific actions, processes, or decisions that produced good outcomes.
   - **What did not work**: Specific problems, delays, errors, or frustrations encountered.
   - **What surprised me**: Unexpected findings, challenges, or outcomes.
   - **What I would do differently**: Concrete changes for next time.
   - Each observation must be specific (not "communication was poor" but "the handoff from collection to grading lacked context on source reliability").

3. **Compile and cluster observations**: Aggregate all individual observations and group them by theme:
   - Process themes (workflow steps that need improvement).
   - Tool themes (tools that helped or hindered).
   - Communication themes (information flow between agents).
   - Quality themes (accuracy, thoroughness, timeliness).
   - Knowledge themes (domain gaps, skill gaps).
   - Count observations per cluster to identify the most common themes.

4. **Analyze what went well**: For the top positive themes:
   - Identify the specific practices that drove success.
   - Determine if these practices are already documented or ad hoc.
   - If ad hoc, formalize them into standard practices.
   - Recognize and reinforce effective behaviors.

5. **Analyze what did not work**: For the top negative themes:
   - Perform root cause analysis (not blame assignment).
   - Distinguish between: things within squad control and external factors.
   - For controllable issues, identify specific process changes to prevent recurrence.
   - For external factors, identify mitigation or early-warning strategies.

6. **Extract lessons learned**: From the analysis, formulate clear lessons:
   - Each lesson must be a complete, actionable statement.
   - Format: "We learned that [observation] because [root cause], so we should [action]."
   - Categorize lessons: methodology, tools, communication, quality, domain knowledge.
   - Prioritize lessons by impact and applicability to future projects.

7. **Update methodology and playbooks**: Based on approved lessons:
   - Revise workflow steps that need modification.
   - Add new checkpoints or quality gates where gaps were found.
   - Update templates and checklists with new best practices.
   - Remove or modify practices that proved ineffective.
   - Version-control all changes so the evolution is traceable.

8. **Identify training needs**: Based on skill or knowledge gaps observed:
   - List specific capabilities that agents need to develop.
   - Identify domain areas where the squad lacks adequate expertise.
   - Recommend training activities (practice exercises, documentation review, specialist mentoring).
   - Set timelines for capability development.

9. **Update the lessons-learned registry**: Add all new lessons to the institutional memory:
   - Tag each lesson with: project ID, date, category, severity, and applicability scope.
   - Link to the specific project artifacts that generated the lesson.
   - Cross-reference with prior lessons to identify recurring patterns.
   - Flag patterns that recur across 3+ projects as systemic issues requiring structural fixes.

10. **Produce retrospective report**: Document the full retrospective:
    - Summary of key findings (top 3 positives, top 3 improvements, top 3 lessons).
    - Detailed observations by theme with analysis.
    - Action items with owners, deadlines, and success criteria.
    - Methodology and playbook changes made.
    - Training needs identified.
    - Comparison to prior retrospectives (are we improving on previously identified issues?).

11. **Track action items to completion**: After the retrospective:
    - Each action item is assigned an owner and a deadline.
    - Progress is tracked in the next retrospective or quality review cycle.
    - Completed actions are verified for effectiveness.
    - Incomplete actions are escalated or re-prioritized.

## Quality Gates
- Every participating agent must contribute individual observations before group discussion.
- Observations must be specific and evidence-based, not general complaints.
- Root cause analysis must be performed for all top negative themes.
- Every lesson must follow the prescribed format (observation, cause, action).
- Methodology changes must be version-controlled and communicated to the squad.
- Action items must have assigned owners, deadlines, and success criteria.
- Retrospective report must compare against prior retrospective findings.

## Outputs
- Retrospective report (findings, lessons, action items).
- Updated methodology documents and playbooks (versioned).
- Updated lessons-learned registry.
- Training needs assessment.
- Action item tracker with owners and deadlines.
- Communication to the squad on changes and improvements.
