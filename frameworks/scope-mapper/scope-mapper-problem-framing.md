# Problem Framing Framework

## Purpose
Guide the Scope Mapper agent through a disciplined process of framing a research problem before any investigation begins. Prevents wasted effort by ensuring the team investigates the right problem, not just the obvious one.

## When to Use
- At the very start of any new research request.
- When a research question feels vague, ambiguous, or too broad.
- When stakeholder intent is unclear or potentially misaligned with the literal question asked.

## Inputs
- Raw research request or question from the user.
- Any contextual information provided alongside the request.
- Domain or industry context if available.

## Process

### Step 1: Identify the Apparent Problem
- Read the request literally. What is being asked on the surface?
- Document the apparent problem in one clear sentence.
- Note any implicit assumptions embedded in the phrasing.

### Step 2: Question Assumptions
- List every assumption the apparent problem carries.
- For each assumption, ask: Is this necessarily true? What if the opposite were true?
- Identify which assumptions are load-bearing (the whole question collapses if they are wrong).
- Flag assumptions that require verification before proceeding.

### Step 3: Identify the Real Problem
- Ask: What decision will this research inform?
- Ask: What would change if the answer were X vs Y?
- Restate the problem in terms of the underlying need, not the surface request.
- If the real problem differs from the apparent problem, document the gap.

### Step 4: Define Success Criteria
- What does a successful answer look like? Be specific.
- What level of confidence is required? (Directional estimate vs precise figure.)
- What format should the output take?
- What is the time constraint?

### Step 5: Validate with Stakeholder
- Present the reframed problem back to the user.
- Confirm that the real problem matches their intent.
- Agree on scope, depth, and success criteria before proceeding.

## Outputs
- A validated problem statement (1-3 sentences).
- A list of confirmed assumptions and flagged uncertainties.
- Explicit success criteria the final deliverable must meet.
- Scope boundaries to hand off to the Scope Bounding framework.

## Common Pitfalls
- Accepting the surface question without interrogation. The stated problem is often a symptom.
- Over-reframing: changing the problem so much that it no longer serves the user.
- Skipping assumption questioning because the problem "seems obvious."
- Failing to define success criteria, leading to unbounded research.
- Not validating the reframe, causing misalignment discovered only at delivery.

## Related Frameworks
- **Scope Bounding**: Once the problem is framed, set explicit boundaries.
- **Issue Tree**: Decompose the framed problem into investigable sub-questions.
- **Question Pyramid**: Structure the hierarchy of questions that flow from the framed problem.
- **MECE for Research**: Ensure the decomposition of the framed problem has no gaps or overlaps.
