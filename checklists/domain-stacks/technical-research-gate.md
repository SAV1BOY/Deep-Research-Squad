# Technical Research Gate

## Purpose

This gate ensures that technical research meets domain-specific quality
standards before delivery. Technical research informs architecture decisions,
technology selections, and engineering strategies that have long-lasting
implications. Inaccurate technical assessments lead to costly rework,
security vulnerabilities, and scalability failures. This gate enforces
precision and depth appropriate for technical decision-making.

## Gate Question

**Does this technical research meet quality standards?**

Technical research must demonstrate accurate understanding of the technologies
evaluated, fair comparison methodologies, awareness of trade-offs, and
practical implementation considerations grounded in verifiable evidence.

## Pass Criteria

1. Technology assessments are based on official documentation and primary technical sources.
2. Performance claims are backed by benchmarks with methodology and environment disclosed.
3. Architecture evaluations address scalability, reliability, security, and maintainability.
4. Technology comparisons use consistent evaluation criteria across all options.
5. Version-specific information is clearly tied to the relevant release or version.
6. Integration complexity and compatibility considerations are addressed.
7. Community health metrics (adoption, contributor activity, issue resolution) are assessed.
8. Licensing implications are identified and evaluated for the use case.
9. Security considerations including known vulnerabilities and patch history are reviewed.
10. Migration paths and lock-in risks are analyzed for each technology option.
11. Total cost of ownership includes infrastructure, licensing, personnel, and maintenance.
12. Practical proof-of-concept or prototype results are referenced where available.
13. The research distinguishes between vendor claims and independent validation.

## Fail Actions

- If assessments rely on unofficial sources, verify against official documentation.
- If benchmark methodology is undisclosed, flag the limitation or seek transparent benchmarks.
- If security review is missing, conduct a vulnerability and patch history assessment.
- If comparisons use inconsistent criteria, standardize the evaluation framework.
- If version information is ambiguous, specify exact versions and note currency.
- If vendor claims are unvalidated, seek independent testing or expert analysis.
- If licensing implications are unexamined, perform a license compatibility analysis.
- If total cost of ownership is incomplete, add missing cost categories.
- Do not deliver technical research until domain-specific standards are met.
