# Technical Tone Profile

## Purpose

This profile defines the writing voice for technical and analytical deliverables.
Precision matters more than brevity. Every term must be unambiguous.

## Core Principles

1. **Be precise.** Use the exact term. Do not substitute for readability if it costs accuracy.
2. **Define on first use.** Every technical term, acronym, or domain-specific concept gets a definition.
3. **Show the methodology.** The reader should be able to reproduce the analysis.
4. **Separate observation from interpretation.** Label which is which.
5. **Use evidence hierarchies.** Distinguish primary data from secondary sources.

## Voice Characteristics

| Attribute         | Target                              |
|-------------------|-------------------------------------|
| Sentence length   | 15-25 words average                 |
| Paragraph length  | 3-6 sentences                       |
| Jargon            | Permitted with inline definitions   |
| Passive voice     | Acceptable for methodology sections |
| Hedging           | Precise (quantified when possible)  |

## Structure Pattern

- **Abstract / Summary:** What was analyzed, what was found, what it means.
- **Methodology:** Data sources, tools, timeframe, scope boundaries.
- **Findings:** Organized by theme or hypothesis, with evidence per finding.
- **Analysis:** Interpretation of findings, patterns, anomalies.
- **Limitations:** What the analysis cannot answer and why.
- **References:** Full source list with access dates.

## Terminology Protocol

When introducing a technical term:
- First mention: full term with definition in parentheses or footnote.
- Subsequent mentions: abbreviated form is acceptable.
- Ambiguous terms: always qualify (e.g., "latency (network-level)" vs "latency (user-perceived)").

## Language Dos

- "We define X as..."
- "The data shows a correlation between A and B (r = 0.73, p < 0.01)."
- "This finding is consistent with / inconsistent with..."
- "The methodology does not account for..."

## Language Don'ts

- "Obviously..." or "Clearly..."
- Undefined acronyms
- Mixing correlation and causation language
- Unquantified comparisons ("significantly better")

## When to Use

- Technical deep dives
- Methodology documentation
- Data analysis reports
- Architecture and system reviews

## Quality Check

Before delivering in technical tone, verify:
- Can a qualified peer reproduce the analysis from this document?
- Are all terms defined on first use?
- Are observations separated from interpretations?
- Are limitations explicitly stated?
